# Jelly Party 2.0 extension privacy and security obligations

Research date: 2026-07-18

This is an engineering/store-policy assessment, not legal advice. It assumes the confirmed design: browser sidebar UI; an optional, per-origin host permission; a UI-free injected video driver; an ephemeral WebSocket party/chat relay; local-only user options; no accounts, database, or history; and server metrics/logs forwarded by Grafana Alloy to Grafana Cloud.

## Decision

The design is publishable in Chrome, Firefox, and Edge without accounts or durable party/chat storage, provided the release does all of the following:

1. Requests only `scripting`, storage, the browser sidebar API, and a runtime-granted permission for the current HTTPS origin (plus the fixed Jelly Party join origin if needed). It must not request `<all_urls>` as a required permission or retain origins “for future use.” Chrome applies its minimum-permission rule to optional permissions too; Firefox and Edge likewise require permissions to be necessary. Runtime optional permissions are the intended mechanism for explaining and granting access at the moment a user starts or joins a party. [Chrome minimum-permission policy](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq), [Chrome Permissions API](https://developer.chrome.com/docs/extensions/reference/api/permissions), [Firefox optional host permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_host_permissions), [Edge developer policy](https://learn.microsoft.com/en-us/legal/microsoft-edge/extensions/developer-policies)
2. Publishes one clear, current privacy policy and makes the store declarations match the code exactly. “No database” does not mean “no data”: Chrome treats locally processed data as handled data, and its examples explicitly include website content, browsing activity, personal communications, and user-generated content. [Chrome user-data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)
3. Explicitly discloses that party nicknames, chat, and playback actions are relayed transiently to the other party participants; that page/video state is read locally to synchronize playback; that options remain in browser storage; and that sanitized operational telemetry is sent to Grafana Cloud. State that there is no account, advertising, sale, profiling, or durable party/chat history.
4. Sends application traffic only over HTTPS/WSS; ships all executable code and UI assets in the extension; retains a strict extension CSP; validates every message boundary; and uses an unguessable party capability (at least 128 random bits), not the current eight-hex-character party ID.
5. Removes sensitive fields before logging. The current server logs `partyId`, generated `uuid`, and `clientName`, and current extension logs include URLs/redirect URLs and party IDs. The current Alloy pipeline forwards whole Docker log lines unchanged. Those are production blockers. The production log schema should contain only timestamp, level, fixed event name, version, coarse error code, and aggregate counters—never chat text, names, party/peer IDs, full or hashed URLs, video titles/source URLs, WebSocket frames, query strings, IP addresses, request headers, cookies, authorization values, or stack traces containing payloads.
6. Keeps the relay ephemeral: party and chat state only in process memory, deleted when the last participant leaves (and bounded by an idle timeout). Only sanitized operations logs go to Grafana Cloud, for the shortest configured retention the plan supports. Grafana currently documents a 14-day minimum for free accounts, while its usage-limit documentation shows that a stack may report a different configured/default retention; verify the actual stack and promise that exact value in the policy. [Grafana retention documentation](https://grafana.com/docs/grafana-cloud/cost-management-and-billing/manage-invoices/understand-your-invoice/logs-invoice/), [Grafana usage limits](https://grafana.com/docs/grafana-cloud/cost-management-and-billing/manage-invoices/understand-your-invoice/usage-limits/)

## What counts as what

| Jelly Party data or operation                  | Store-policy classification                                                                                                            | Required treatment                                                                                                                                                                                                                               |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Chat text                                      | **Personal communications**; also user-generated content under Chrome                                                                  | Declare it. Relay only to the current party, never log it, never permit routine human access, and discard immediately after forwarding.                                                                                                          |
| Participant nickname                           | Potential **personally identifying information**, because users may enter a real name                                                  | Declare conservatively. Relay only to party peers, keep in memory only, and never log it.                                                                                                                                                        |
| Play/pause/seek and playback position/duration | Firefox **website activity** and plausibly **website content**; Chrome website content/resources and user activity                     | Declare conservatively. Transmit only the minimum state needed for synchronization; no analytics label may contain it.                                                                                                                           |
| Current origin, URL, title, video URL/title    | **Browsing activity** and/or **website content**                                                                                       | Read locally only when needed. Do not send it to the relay or Grafana. Avoid putting the target URL in an HTTP query string. Put it in the join URL fragment (not sent in HTTP requests) or keep it entirely extension-to-extension/user-shared. |
| Local nickname/emoji/preferences               | Chrome user data even when stored locally; not a Firefox `data_collection_permissions` category unless transmitted outside the browser | Cover in the privacy policy. Use local extension storage, not sync storage, unless sync is deliberately disclosed. Provide reset/remove controls.                                                                                                |
| IP address and connection metadata             | Potential personal data under general privacy law and Edge's broad personal-information definition                                     | Do not put it in application/Caddy logs. Disclose transient network processing by the VPS. If the hosting provider keeps infrastructure logs, disclose its actual retention.                                                                     |
| Aggregate party/client/message-type counters   | Operational technical data when no stable identifier, URL, party ID, or payload is attached                                            | Safe for Grafana metrics. Keep labels low-cardinality and fixed. Do not add party, peer, origin, or URL labels.                                                                                                                                  |

Mozilla's current taxonomy is especially direct: chat messages are `personalCommunications`; URLs/domains are `browsingActivity`; visible/embedded video and page material is `websiteContent`; clicking/typing/actions are `websiteActivity`; and extension usage, settings, errors, and device/browser facts are `technicalAndInteraction`. [Firefox taxonomy](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/#taxonomy)

## Store declarations and consent

### Chrome Web Store

- Complete the Privacy practices disclosure and Limited Use certification. At minimum, conservatively select the categories corresponding to personally identifiable information (nickname), personal communications (chat), user-generated content, website content, and user activity; select web history/browsing activity only if a URL/domain ever leaves the browser. Re-check the dashboard's exact category names at submission.
- Link the privacy policy from the Developer Dashboard and put a Limited Use statement on the product homepage or one click away. The policy must cover automatically collected server/HTTP logs, not only explicit form data. Dashboard, policy, listing, and runtime behavior must agree. [Chrome user-data and Limited Use requirements](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)
- The single purpose should be: “Synchronize video playback and chat with people in a party the user starts or joins.” Host access and data transmission are allowed only to provide, maintain, secure, or measure that purpose. No advertising/profiling and no unrelated analytics. Chrome forbids routine human reading of user data except narrow consent/security/legal/aggregated exceptions. [Chrome Limited Use requirements](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq#limited-use)
- Chat and playback relay are prominent, expected core behavior, so Chrome's extra in-product “prominent disclosure and affirmative consent” rule should not require a separate legal modal if the listing and sidebar clearly say what is shared before the user starts/joins. The explicit Start/Join action should be the operational consent point. Any optional client telemetry would be unrelated enough to require a separate, prior opt-in; omit it for launch.

### Firefox / AMO

- Target Firefox 140+ and use the built-in data-collection consent system. New AMO extensions have required it since 2025-11-03, and Mozilla says older add-ons will have to migrate later. Existing add-ons may currently be exempt, but adopting it now avoids a second migration. [Firefox built-in consent](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/)
- Declare the transmitted categories conservatively as required: `personalCommunications`, `personallyIdentifyingInfo`, `websiteActivity`, and `websiteContent`. Omit `browsingActivity` only after proving that no URL/domain is sent to Jelly Party infrastructure. If client telemetry is later added, `technicalAndInteraction` must be optional, never required. The manifest field is `browser_specific_settings.gecko.data_collection_permissions`. [Firefox manifest reference](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings#data_collection_permissions)
- Required data is shown at installation and refusal cancels installation. That is appropriate because chat/playback relay is the product. Do not rely on Mozilla's implicit-consent exception: `personalCommunications` is explicitly ineligible, and party connections are continuous rather than one-shot. [Firefox taxonomy and required data](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/#required-data)
- The AMO listing must plainly describe what is transmitted. Provide reviewers with reproducible build instructions/source if the package is bundled/minified and complete test instructions that need no paid media account (for example, a public HTML5 video test page). Mozilla requires reviewable source and functional test information. [Mozilla add-on policies](https://extensionworkshop.com/documentation/publish/add-on-policies/)

### Microsoft Edge Add-ons

- In Partner Center's Privacy page, provide a narrow Single Purpose statement, justify each manifest permission, declare **No remote code**, select every applicable user-data category, certify limited use, and link an accessible current privacy policy. Microsoft documents this exact submission flow and warns that incomplete or inconsistent disclosures delay or fail certification. [Edge publishing privacy flow](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension#step-6-enter-privacy-information)
- The Edge policy treats web browsing activity as personal information, requires secure transport, requires an accurate policy covering third-party services, and prohibits future-proof permissions. [Edge developer policy](https://learn.microsoft.com/en-us/legal/microsoft-edge/extensions/developer-policies)
- Grafana must be identified as the observability service provider. To avoid Edge's stricter third-party opt-in problem, do not send client-side telemetry and ensure Alloy receives no extension user data—only sanitized server operational events and aggregate metrics. If user-linked telemetry is ever sent to Grafana, obtain an in-product opt-in/opt-out and confirm the processor terms before shipping it.

## Permission-minimizing implementation

- Keep `storage` local; use the sidebar APIs and runtime messaging without extra permissions where the browser permits.
- Use `scripting` plus `optional_host_permissions`, request exactly `https://current-origin/*` from a user gesture when the user presses Start/Join, and explain that it allows Jelly Party to find and control the video on that site. Never request HTTP origins for production media sites unless a supported use case truly requires them. Optional permissions can be revoked and must be handled gracefully. [Chrome Permissions API](https://developer.chrome.com/docs/extensions/reference/api/permissions), [Firefox optional host permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_host_permissions)
- Consider `activeTab` for the host's explicit Start action because it grants temporary access from a user gesture; keep optional origin permission for join/reconnect behavior only if persistence is actually necessary. Chrome's scripting API accepts either host permission or `activeTab`. [Chrome scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting)
- The page driver should read/control only the chosen `HTMLVideoElement`. Do not inspect page text, cookies, storage, requests, or authentication state. Keep service-specific drivers behind the same narrow contract.
- Do not add `tabs`, `webNavigation`, cookies, webRequest, history, broad host access, or externally connectable access unless a concrete launch feature proves the need.

## Security requirements

### Extension package and CSP

- Bundle all JavaScript, Wasm, fonts, CSS, and executable behavior. MV3 in Chrome/Edge does not allow remotely hosted executable code; Mozilla requires add-ons to be self-contained and forbids remote code. Server JSON may carry party data, not logic that is evaluated or used to construct executable code. [Chrome remote-hosted-code guidance](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code), [Mozilla add-on policies](https://extensionworkshop.com/documentation/publish/add-on-policies/), [Edge MV3 declaration](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension#declare-any-use-of-remote-code)
- Remove the current Google Fonts `@import` statements from extension CSS and package fonts locally (or use system fonts). Besides making the package less self-contained, each remote font request leaks extension use/network metadata to Google.
- Keep a strict extension CSP: at least `script-src 'self'; object-src 'self'`; constrain `connect-src` to the production WSS endpoint and any genuinely required Jelly Party HTTPS origin; use local styles/fonts/images. Do not relax a website's CSP. Chrome content scripts in isolated worlds inherit an extension CSP that blocks `eval` and external scripts, while main-world scripts inherit the page CSP; prefer the isolated world unless a proven driver requires otherwise. [Chrome content-script CSP](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#content-security-policy), [Mozilla CSP policy](https://extensionworkshop.com/documentation/publish/add-on-policies/#development-practices)

### Message and relay boundaries

- Replace the current wildcard `window.postMessage(..., "*")` bridge with extension runtime messaging as already decided. Validate message schemas, types, ranges, size, `sender.id`, tab/frame identity, and party state before acting. Never pass arbitrary page data into privileged APIs.
- Use `https://` and `wss://` only, current TLS, no mixed content. Chrome, Mozilla, and Edge all require modern encrypted transport for this data. [Chrome secure-handling requirement](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq), [Mozilla add-on policies](https://extensionworkshop.com/documentation/publish/add-on-policies/#development-practices), [Edge developer policy](https://learn.microsoft.com/en-us/legal/microsoft-edge/extensions/developer-policies)
- Party links are bearer capabilities. Generate at least 128 random bits, use constant-time/opaque handling where practical, cap message size, rate-limit joins/chat/actions per connection/IP without retaining raw IPs, impose connection/party limits, and expire idle parties. The current `crypto.randomUUID().slice(0, 8)` exposes only 32 random bits and is not sufficient.
- The relay must never echo malformed payloads, trust client timestamps/types blindly, or log raw exceptions containing frames. Escape chat on rendering (text nodes, not HTML) and enforce a small maximum length server-side.
- Keep metrics on a private Docker network; do not expose the Prometheus port publicly. Protect Grafana credentials as secrets, use a least-privilege token, rotate it, and restrict Grafana access with MFA.

## Logging, Grafana, and retention

The safest launch posture is **no client telemetry** and a server allowlist logger. Redaction after the application logs data is only defense in depth; the application should never emit it.

- Change server logging to fixed event codes such as `server_started`, `connection_opened`, `party_created`, `protocol_error`, with no identity/content fields. If abuse rate limiting needs an IP-derived key, keep a short-lived in-memory keyed HMAC and never log/export it.
- Add an Alloy `loki.process` allowlist/drop pipeline before export. Grafana documents filtering/dropping and output replacement, plus a secret filter, but generic secret detection will not recognize party IDs, names, URLs, or chat; explicitly remove those at the producer and test with canary values. [Grafana Alloy log processing](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.process/), [Grafana Alloy secret filter](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.secretfilter/)
- Keep metric labels fixed (`type` must be a validated enum), never arbitrary client strings. Aggregate counters may have a longer service-defined lifetime because they are non-identifying; do not label them with party, peer, origin, media, or IP values.
- Configure Grafana Cloud in an EU region where available, accept/review Grafana's DPA and subprocessors, restrict staff access, and disclose Grafana in Jelly Party's policy. Grafana publishes a DPA and notes that EU regions are available. [Grafana DPA](https://grafana.com/legal/data-processing-agreement/), [Grafana subprocessors](https://grafana.com/legal/list-of-subprocessors/)
- Adopt the shortest available log retention (target 14 days; disclose the verified configured value), then automatic deletion. Do not promise immediate deletion if Grafana's actual plan retains longer. General EU privacy principles require purpose limitation, data minimization, security, and identifiable data to be kept no longer than necessary. [GDPR Article 5](https://eur-lex.europa.eu/eli/reg/2016/679/2016-05-04/eng)

## Privacy-policy minimum contents

Publish a concise page at a stable first-party URL and link the same policy in all three stores. It should state:

- Controller/publisher identity and contact address.
- Data handled locally: current page/video playback state and local nickname/emoji/options.
- Data transmitted: nickname, emoji, chat text, playback action/position, ephemeral party capability, connection metadata necessarily processed by the network; exact recipients (current party participants, Jelly Party VPS, hosting/network providers) and purpose.
- Observability: sanitized operational events/aggregate metrics are sent through Alloy to Grafana Cloud; list actual fields, region, and verified retention.
- No account, database, advertising, sale, profiling, durable chat/party history, cookies for tracking, or client analytics at launch.
- Storage/retention: party/chat disappears from relay memory after forwarding/party teardown; local options remain until changed/uninstalled/reset; infrastructure and sanitized log retention stated accurately.
- Security summary: HTTPS/WSS, least privilege, no remote code.
- User controls: leave party stops relay processing; revoke site permission; reset local options; contact route for access/deletion/privacy requests. Explain that relayed messages already delivered to another participant cannot be recalled from that participant's browser.
- Limited Use statement: data is used and transferred only to provide, maintain, secure, or measure Jelly Party's disclosed watch-party purpose; it is not used for advertising and is not routinely read by humans.
- Effective date and change process. A later expansion (accounts, analytics, crash reports, history, moderation storage, voice/video) requires a new data review, declarations, policy update, and consent before collection begins.

## Production acceptance checklist

- [ ] Required manifest permissions are audited; page hosts are runtime optional and origin-specific.
- [ ] Firefox manifest declares the required data categories and is tested on Firefox 140+ install flow.
- [ ] Store listing, in-sidebar Start/Join copy, privacy policy, and all three reviewer declarations agree.
- [ ] No URL is placed in the join service's query string or logs; use a fragment/client-side transfer.
- [ ] Chat, nickname, party ID, peer ID, URLs, source/title, IP, headers, and payloads cannot reach stdout, Caddy logs, Alloy, or Grafana (verified with automated canary tests).
- [ ] Google Fonts and every other remotely loaded extension asset/code path are removed.
- [ ] Extension CSP and WSS/HTTPS endpoint allowlists are verified in release packages.
- [ ] Wildcard page messaging is gone; message schemas/senders and server payload limits are validated.
- [ ] Party token has at least 128 random bits; idle expiry, limits, and rate limiting are enabled.
- [ ] Relay has no durable party/chat store and erases in-memory parties on teardown/timeout.
- [ ] Grafana region, DPA/subprocessors, access controls, exact retention, and privacy-policy wording are verified.
- [ ] Chrome Privacy practices/Limited Use, Firefox data collection manifest, and Edge Privacy page are captured in a release checklist for every update.
